# Mortgage Origination & Underwriting Data Pipeline

This project implements the mortgage application and underwriting pipeline described in the Deutsche Bank data engineering case study. It follows a Bronze-Silver-Gold medallion architecture using Snowflake, dbt, Terraform, and Airflow.

## Architecture overview

```text
+--------------------+        +--------------------+        +--------------------------+
|  Source systems    |        |  Snowflake Bronze  |        |       dbt Silver          |
|  - mortgage apps   | ----> | raw JSON landing   | ----> | join + clean + mask PII   |
|  - credit bureau   |        | raw CSV landing    |        | technical_rejections      |
+--------------------+        +--------------------+        +-----------+--------------+
                                                                         |
                                                                         v
                                                            +--------------------+
                                                            | dbt Gold           |
                                                            | underwriting       |
                                                            | decision log + HMDA|
                                                            +--------------------+
```

## Solution summary

- Ingestion: JSON and CSV sources are simulated and landed into Snowflake Bronze tables.
- Processing: dbt models clean, join, validate, and mask sensitive fields.
- Business logic: LTV, DTI, and FICO rules route applications into approval, decline, or co-signer-required workflows.
- Security: Snowflake masking policies and RBAC protect SSN and applicant names.
- Orchestration: Apache Airflow runs the pipeline with dependency checks and alerting.
- IaC: Terraform provisions Snowflake objects and access policies.

## Business rules

The underwriting logic follows the case study specification:

- LTV = (Loan Amount / Property Value) * 100
- DTI = (Monthly Debt / Monthly Gross Income) * 100
- Decline if LTV > 95%
- Decline if DTI > 43%
- Decline if FICO < 620
- If FICO is between 620 and 660 and DTI is between 36% and 43%, mark as Requires Co-signer
- Every pipeline decision is logged in Gold with a reason code

## Calculation logic

The core formula implementation is in `src/underwriting_rules.py` and is also reproduced in the Gold dbt model logic.

Example:

- Loan amount = 360,000
- Property value = 400,000
- LTV = 360,000 / 400,000 * 100 = 90%
- Monthly debt = 2,000
- Monthly gross income = 4,500
- DTI = 2,000 / 4,500 * 100 = 44.44%
- Result: Declined due to DTI exceeding 43%

## Data examples

The project includes synthetic sample data in the `data/` folder. Names use generic applicant labels and SSNs use `TEST-SSN-*` values; these are generated by `scripts/generate_sample_data.py` and are not real personal data.

## Design answers

### 1) Credit bureau API delay

If the credit bureau API is delayed, the application data should land to Bronze first and remain in an `application_pending_credit` state. The orchestrator should wait for the credit-bureau file to land before triggering the dbt Silver transformation. This avoids partial joins and keeps the pipeline deterministic. A common pattern is to add a landing-status table or rely on Airflow sensors to confirm both source files are present before dbt runs.

### 2) Snowflake Time Travel for approvals

Snowflake Time Travel can snapshot the state of the Gold or Silver tables at the exact approval time. For example, if an application was approved 30 days ago, the historical query can use `AT | TIMESTAMP => ...` or a `AS OF` clause to inspect the applicant’s credit and income profile at that precise point in time for audit and compliance investigations.

### 3) End-of-quarter spike scenario

The design scales horizontally by partitioning raw data landing into Snowflake stages, using auto-suspend warehouses, and leveraging Snowpipe or external stages for ingestion. dbt can run in incremental mode for high-volume transforms, while the Airflow DAG can fan out tasks and use concurrency-safe scheduling. For a 1,000x surge, Snowflake’s elasticity and multi-cluster warehouses ensure the pipeline remains resilient without a redesign.

## Setup steps

1. Install dependencies:
   `pip install -r requirements.txt`
2. Generate sample input data:
   `python scripts/generate_sample_data.py`
3. Print underwriting decisions for the sample applications:
   `python scripts/show_sample_decisions.py`
4. Run unit tests:
   `pytest tests/test_underwriting_logic.py`
5. dbt project configuration:
   - set `DBT_SNOWFLAKE_ACCOUNT`, `DBT_SNOWFLAKE_USER`, `DBT_SNOWFLAKE_PASSWORD`, and optionally `DBT_SNOWFLAKE_ROLE` in the environment. The dbt profile reads credentials from environment variables.
6. Terraform:
   - provide `snowflake_account`, `snowflake_username`, and `snowflake_password` through Terraform variables or `TF_VAR_*` environment variables; do not commit credentials.
   - run `terraform init` and `terraform plan`
